# TensorRT FP16 对照与后续决策

## 阶段前提

必须先冻结四模型 PyTorch FP16 结果，以及三个接口各自的实例/并发曲线。第一轮选择一个代表模型验证导出、shape、输出和加载流程，再推广至人数、人脸、学生行为、教师行为四模型。

不在基线 `vbas` 环境升级依赖。`vbas-trt` 中选择与实际驱动、CUDA runtime、Ultralytics 8.3.156、YOLO 模型算子兼容的组合，先验证再固定版本。不能直接套用最新 Ultralytics 导出参数。

## 迁移顺序

1. 核实各模型实际 shape 和输出、类别映射及加密加载/临时文件生命周期。
2. 在指定 3090 上导出并构建 FP16 engine，保存源模型、ONNX（如使用）、引擎哈希和构建日志。
3. 调整后端加载与 warmup；不能仅将 `.pt` 改为 `.engine` 并沿用 PyTorch 专用 `.to(device)`。
4. 第一轮保留现有业务处理、阈值和 NMS 语义，验证三接口 schema 及完整结果。
5. 对同一输入集合执行全量结果对照和人工标注评估，再执行各接口独立压测协议。
6. 需要时另开实验评估输入 profile、batch 或 NMS 融合，每次只改变明确因素。

## 公平比较与容量比较分开

| 对照 | 固定条件 | 结论 |
|---|---|---|
| 同配置对照 | 同一 shape、batch、实例、并发、输入方式和业务配置 | 后端变化带来的收益 |
| 各自最佳配置 | 数据和精度要求相同，分别搜索实例/并发 | 实际可达到的容量与资源成本 |

动态 profile 应来自真实输入分布，记录 min/opt/max。固定 shape 引擎若改变了现有预处理，应给 PyTorch 设置同 shape 对照，并将原业务路径变化单独报告。模型微基准、完整接口和多实例容量分别展示。

比较后端的公共指标使用 GPU/进程外部统计；PyTorch allocated/reserved 不能直接与 TensorRT 内存池统计对等。引擎构建耗时、首次加载、预热及稳态性能分开。

## 交付与回退

每个引擎记录 GPU UUID/型号、TensorRT/CUDA/驱动版本、构建选项、精度、profile、模型哈希。迁服务器时检查兼容性或重建，不能假设 engine 跨所有机器可用。

后端选择由明确配置控制，保留 PyTorch FP16 回退路径；测试时禁止静默回退。已有接口字段、错误语义、类别和坐标约定保持一致。

## C++ 决策

完成 TensorRT 对照后再分析剩余 CPU、数据复制、调度和序列化成本。如已满足业务容量与延迟要求，保留 Python。若存在明确瓶颈，再分别评估局部原生模块和完整 C++ 服务，不预先承诺重写。
