## 实现约束

使用原load.py执行HTTP，仅在显式协调模式增加启动屏障、分片序号与开放式相位；不传新参数时沿用原路径。协调器只允许1或2个进程，总实例、总C及总rate均匀分片，分片不共享服务端口。各子进程先完成输入读取及HTTP客户端初始化，再报告ready；父进程统一发布同一单调时钟起点与Unix时间，所有正式记录使用共同窗口。双进程的开放式到达相差1/总rate，避免同时突发成对请求。

同seed洗牌后，逻辑序号按分片交错，开放式保护槽亦占有原计划序号。保留各分片原始请求与摘要，父进程对同一窗口的原始请求重新计算计数、吞吐及P50/P95/P99，不平均分位数或相加异窗吞吐。原普通load.py序号口径不变，协调模式另记身份和源文件哈希，不覆盖历史结果。

instances.py仅显式选择协调模式时调用新工具；采样需区分协调父进程和实际发生器子进程，清理需覆盖本轮整个发生器进程组。控制失败、子进程提前退出或摘要/请求不一致保留原件并报错；真实HTTP/业务失败保留并汇总，不更改服务准入或队列。

## 验证顺序

1. CPU loopback单/双进程：同计划序号、相位、种子与图片映射，统一窗口，核对原始统计。
2. CPU实际429、启动失败及终止清理；确认失败未丢弃、未遗留子进程、既有默认调用仍可用。
3. 无模型回归及源码检查；记录版本和工具哈希后提交perf。
4. 网络恢复后先检查服务器原任务。原TRT结束且GPU空闲才同步新工具，按02固定条件开展真实GPU对照；CPU通过不能替代GPU验证或容量结论。
