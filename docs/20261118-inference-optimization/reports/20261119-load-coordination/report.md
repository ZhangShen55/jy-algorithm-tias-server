# 单/双发生器协调工具

状态：协调代码及instances.py显式入口已实现；本机25项无模型回归通过，其中8项覆盖真实CPU loopback及进程控制。服务器Linux资源采样与真实GPU对照仍未验证，不能据此认定发生器瓶颈已解决。

## 实现约束

使用原load.py执行HTTP，仅在显式协调模式增加启动屏障、分片序号与开放式相位；不传新参数时沿用原路径。协调器只允许1或2个进程，总实例、总C及总rate均匀分片，分片不共享服务端口。各子进程先完成输入读取及HTTP客户端初始化，再报告ready；父进程统一发布同一单调时钟起点与Unix时间，所有正式记录使用共同窗口。双进程的开放式到达相差1/总rate，避免同时突发成对请求。

同seed洗牌后，逻辑序号按分片交错，开放式保护槽亦占有原计划序号。保留各分片原始请求与摘要，父进程对同一窗口的原始请求重新计算计数、吞吐及P50/P95/P99，不平均分位数或相加异窗吞吐。原普通load.py序号口径不变，协调模式另记身份和源文件哈希，不覆盖历史结果。

instances.py仅显式选择协调模式时调用新工具；采样需区分协调父进程和实际发生器子进程，清理需覆盖本轮整个发生器进程组。控制失败、子进程提前退出或摘要/请求不一致保留原件并报错；真实HTTP/业务失败保留并汇总，不更改服务准入或队列。

## 验证顺序

1. CPU loopback单/双进程：同计划序号、相位、种子与图片映射，统一窗口，核对原始统计。
2. CPU实际429、启动失败及终止清理；确认失败未丢弃、未遗留子进程、既有默认调用仍可用。
3. 无模型回归及源码检查；记录版本和工具哈希后提交perf。
4. 网络恢复后先检查服务器原任务。原TRT结束且GPU空闲才同步新工具，按02固定条件开展真实GPU对照；CPU通过不能替代GPU验证或容量结论。

## CPU验证记录（北京时间2026-11-19）

本机Python3.12.9、httpx0.28.1。执行`python3 -m unittest discover -s tests/benchmark -p 'test_*.py'`：25项通过；三个改动脚本py_compile与git diff --check通过。新增8项包含真实单/双HTTP的同序号/图片/相位/共同起点、原始合并P95、HTTP429保留、本地保护槽、闭环及普通load默认调用、非均匀分片/审计冲突拒绝、启动失败清理与SIGTERM后子进程回收。测试使用临时合成单图JSON，不读取课堂照片、不导入模型、不接触GPU。

测试先观察协调脚本缺失导致预期失败，再实现；manager入口先观察缺少参数导致失败，再接入。自查发现聚合mode若加coordinated前缀会让既有离线工具误判开放式，新增失败断言后修正为兼容的open_loop前缀，协调身份另用load_processes/manifest保留。最后25项通过。临时CPU响应不作为容量证据留存；测试代码可重新执行，正式GPU原始证据另存新run_id。

显式调用方式：在既定instances.py命令增加`--load-processes 1`或`--load-processes 2`，其余I/C/b/rate/seed/预热/时长不变；只有新诊断调用生效，原调度不自动选择它。分片父进程role为load_coordinator，实际子进程为load_generator；/proc采样路径及整个进程组清理由服务器Linux/GPU验证继续确认。仍须在每轮前保留原主机内存预算和指定GPU空闲检查，不因分成双发生器而放宽保护。
