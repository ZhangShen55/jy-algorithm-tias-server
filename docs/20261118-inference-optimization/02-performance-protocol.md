# 三接口独立压测协议

## 测试单元

三个接口分别完整执行本协议，单轮只压其中一个接口：

| 接口 | 图片 |
|---|---|
| `/SyncTasks2` | 学生画面，人数检测 |
| `/ImageDetect/student/v1.0.0` | 学生画面，学生行为及接口附带检测结果 |
| `/ImageDetect/teacher/v1.0.0` | 教师画面，教师行为 |

一个实例定义为一个独立服务进程、一个监听端口、一个 Uvicorn worker。记录每个进程实际加载的模型；当前全局初始化可能让每个实例加载四模型，必须验证，不能只按被测接口的模型估算显存。

`C` 表示整组实例的总在途 HTTP 请求数，不是每实例并发。`I=8,C=48` 初始平均每实例 6 个请求。采用无重试、无隐式排队的可追踪分发方式，记录各实例收到的请求数量和延迟。

主实验每请求一张图，模型 batch=1；先检查接口允许此调用方式。单请求多图和模型批量分别作为后续实验，不混入主结果。主容量实验固定为同一输入方式，优先 Base64；URL 下载与文件读取成本另测。

## 搜索步骤

1. 先运行 `I=1,C=1` 完成功能和基础显存检查，确认结果有效后再尝试 `I=8,C=48`。
2. 逐个装载实例并监测显存。如 8 实例无法装载，记录装载失败边界，下降到 4、2、1 找可行点；不把 OOM 当作零吞吐数据。
3. 固定实例数，由总并发 48 开始探索；若已拥堵则向 24、12、6 等下降，若未到拐点则向 72、96 等增加，并在拐点附近细化。以实际结果调整步长。
4. 实例数先围绕 8 探索 4、8、12，必要时继续扩展或缩小。每个实例数都重新搜索并发，不能只固定 48 就宣布找到了实例峰值。
5. 对候选峰值及其相邻配置重复至少 3 轮；固定预热方法、样本序列、配置和初始状态，运行顺序交错以减少热状态偏差。
6. 候选配置做 30～60 分钟稳定性测试，最终分别报告每实例数下的最佳并发，以及全局实测最佳组合。结论限定在已搜索范围内。

探索轮建议预热至少 30 秒且每模型实际 shape 有足够调用，随后稳态采样至少 3 分钟。确认轮不少于 5 分钟；低吞吐场景延长时间确保样本数。每轮记录有效样本数，P99 样本不足时标注限制。

## 撞墙的三个含义

1. **容量拐点**：增加负载后吞吐接近平台，延迟或排队继续增加。默认探索规则：相邻档吞吐增益小于 5%，同时 P95 增长超过 20% 或排队持续增长，复测确认；该规则是操作性定义，不是硬件物理峰值或生产 SLO。
2. **硬失败边界**：OOM、实例启动失败、持续超时或服务错误。立即停止增加负载，保存日志、已完成与未完成请求数量。
3. **撞墙发生时间**：从该轮正式施加负载开始，到首次出现持续拥堵区间的经过秒数；同时报告当时的请求延迟。没有发生则写“在观察窗口内未出现”，不虚构一个时间。

并发固定的闭环压测适合找容量曲线，但会在响应变慢后自动减少发送速率，可能低估排队影响。找到候选吞吐后，补充定速开放式实验，例如候选容量的 80%、100%、110%，记录计划发送时间、实际发送时间与完成时间。

开放式实验默认用连续 3 个 10 秒窗口中积压持续增加识别持续拥堵，并记录窗口及检测规则。SLO 确定后另报告首次持续违反 SLO 的时间。设置有界在途数、队列上限及超时，超过测试保护上限终止该轮；不得丢弃超时后仍称吞吐稳定。

## 指标口径

- 请求延迟：客户端发送到完整接收响应的 wall-clock 时间，P50/P95/P99/平均值及最大值。开放式实验另外记录从计划发送时刻计算的延迟，暴露负载生成器跟不上问题。
- 单张图片时间：服务端每图片处理耗时及分位数；主实验一请求一图，另外报告客户端每图延迟。多图请求不能用请求 P95 除以图片数量获得每图 P95。
- 吞吐：稳态成功图片数/采样秒数，同时报告请求数、错误率、超时和未完成数。`1000 / 图片吞吐` 只是平均产出间隔，不能称为单图响应耗时。
- 资源：各实例及总 CPU/RSS、GPU 利用率时间序列、GPU 总显存与进程显存、PyTorch allocated/reserved 峰值、功耗/温度/频率。
- GPU 利用率不等于实际 FLOPS 利用率。需要解释空隙、搬运和计算重叠时，使用短时 profiler 实验，不把 profiler 结果当正常吞吐。
- 负载生成器记录 CPU、发送速率和连接数；连接池、超时、客户端数量、网络位置保持一致，避免把客户端瓶颈误判为服务峰值。

## 分段测量

阶段：请求接收/解析、资源排队、读取/下载、Base64/JPEG 解码、ROI、模型预处理、H2D、网络执行、NMS/坐标恢复、D2H、业务聚合、响应序列化。

CPU 用单调时钟；GPU 用实际 stream 上的 CUDA Events。日常指标与独立诊断模式分开，不在并发吞吐测试中逐阶段强制同步 GPU。并行模型耗时不可直接相加作为请求总时间。所有统计通过 request_id、image_id、model、instance_id、run_id 关联，不改变业务响应。
