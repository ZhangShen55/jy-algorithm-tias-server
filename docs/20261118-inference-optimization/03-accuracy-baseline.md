# PyTorch FP16 精度基线与结果留存

## 数据冻结

对服务器 `tests/` 下 JPG 建立清单：相对路径、SHA256、尺寸、学生/教师场景、原始来源/连续帧组、适用接口、请求阈值和 ROI。不依赖绝对路径识别同一图片。

检查重复和近似重复、无法解码样本、分辨率分布及类别覆盖。划分快速回归、性能、人工标注评估三种用途；同一图片可以有多个用途，但标注统计需要说明相似帧带来的偏差。

现有图片没有发现标注文件：PyTorch 输出是参考结果，不是真实标签。人工标注完成前只报告检测结果一致性、数量差异和案例，不使用“真实准确率”描述。

## 基线生成

固定代码、模型 SHA256、FP16 设置、输入 shape、letterbox、NMS、max_det、类别映射、ROI、阈值及请求内容，对三个接口分别生成全量可用图片结果。记录错误和排除原因，禁止静默漏样本。

基线首先采用低并发顺序执行，使结果采集与容量测试解耦；对一部分图片重复执行，检查基线自身稳定性，再抽样比较多实例高并发结果，识别模型共享或并发导致的差异。

对每次图片/接口调用保存：

- run_id、dataset_id、image_id/图片哈希、接口、请求参数与模型版本。
- 原始模型检测结果：类别 ID/名称、浮点置信度、浮点 xyxy；记录结果位于 NMS 前还是 NMS 后，以及坐标所处空间。
- 至少保留 NMS 后、业务阈值过滤前的模型框；如需原始网络张量，仅对诊断样本额外保存，避免全量大张量膨胀。
- 业务过滤及教师主体聚合后的结果、完整接口响应、错误详情。
- 关键样本可视化图与 PyTorch/TensorRT 差异可视化；不以可视化代替结构化结果。

接口响应未包含置信度时，必须从内部结果另行采集。保留原有响应语义，不向正式接口添加调试字段。

## 存储约定

原始数据使用 JSONL（或明确 schema 的等价格式），每个 run 独立目录；模型、图片、清单和结果通过哈希关联。结果只新增，不覆盖已冻结的 PyTorch 基线。

原始全量结果、图片及引擎放服务器独立产物目录 `/home/zhangs/workspace/vbas-benchmarks/<run_id>/`；Git 保存方案、脚本、schema、摘要报告和产物哈希/位置，避免分支切换影响原始证据。基线完成后生成校验清单并备份，后续迁服务器复制产物后验证哈希。

## 对照方法

- 模型层：按类别进行一对一框匹配，保存 IoU 阈值及匹配算法配置；报告匹配比例、置信度差、坐标差、基线有而候选无、候选新增的检测。
- 业务层：比较人数、人脸计数、各类学生行为数量、教师主体数及行为聚合结果。重点审查阈值附近、密集小目标、遮挡和重叠框。
- 人工标注层：各类 Precision/Recall/mAP，人数 MAE 和计数误差分布；指标的 IoU、置信度定义随报告保留。业务响应可能不足以计算完整 AP，应使用模型级浮点框和置信度。
- 单独记录 NaN/Inf、空结果、错误类别和越界坐标；性能提升不能掩盖结果异常。

具体可接受的业务差异和准确率下降门槛，在查看基线与标注覆盖后确定，并在 TensorRT 正式验收前冻结。不要求 FP16 后端逐位相同，也不自动接受所有数值差异。
